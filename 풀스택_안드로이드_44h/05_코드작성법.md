# ⌨️ 코드를 "어떻게" 작성하는가 — 3트랙 공통 실전 규칙

> 강의를 100개 봐도 실력이 안 느는 이유는 **코드를 쓰는 방식**이 잘못돼서입니다.
> 이 문서가 이 플랜에서 가장 중요합니다. **매주 한 번씩 다시 읽으세요.**

---

## 1. 4단계 학습 사이클 (모든 진도에 예외 없이 적용)

| 단계 | 하는 일 | 시간 비중 | 절대 규칙 |
|------|---------|-----------|-----------|
| **① 이해** | 강의/문서를 본다. 코드는 안 친다 | 20% | 배속 1.25x 이하. 2x는 아무것도 안 남습니다 |
| **② 따라치기** | 강사와 똑같이 친다 | 20% | **복붙 금지.** 손가락이 기억해야 합니다 |
| **③ 백지 재구현** | 강의를 끄고, 아무것도 안 보고 다시 만든다 | 40% ⭐ | **여기가 진짜 학습.** 막히면 5분 고민 후 딱 그 부분만 확인 |
| **④ 변형 과제** | 요구사항을 하나 바꿔서 다시 만든다 | 20% | "삭제 기능 추가", "정렬 조건 변경" 등 |

> ⚠️ **초보자의 90%는 ①②만 하고 진도를 나갑니다.** 그래서 3개월 뒤 빈 파일 앞에서 손이 안 움직입니다.
> **③을 못 하면 그 진도는 안 배운 겁니다.** 다음 날 다시 하세요.

### 실전 적용 예시 — "React To-Do" 진도 (총 5시간)

```
1h  강의 시청 (손 안 댐, 필기만)
1h  강사 따라 치기 (완성)
2h  프로젝트 폴더 삭제 → 백지에서 다시 (막히면 5분 룰)
1h  변형: "완료 항목만 필터링" + "localStorage 저장" 추가
    → 커밋 + TIL 3줄
```

## 2. 백지 재구현을 통과하는 방법 — "설계를 먼저 말로"

코드를 치기 전 **종이나 주석에** 이걸 먼저 씁니다. 3분이면 됩니다.

```
1) 무엇을 만드는가         : 책 목록 화면
2) 필요한 데이터            : Book(id, title, author, isRead)
3) 데이터는 어디서 오는가   : GET /api/books
4) 상태는 무엇이 변하는가   : books[], isLoading, error
5) 사용자가 하는 행동       : 목록 보기, 클릭해서 상세, 읽음 체크
6) 화면을 어떻게 쪼개는가   : BookListPage > BookList > BookItem
```

> 이 6줄이 **면접에서 "이 프로젝트 설명해주세요"의 답변 골격**과 정확히 같습니다.
> 코드를 먼저 치는 습관은 8개월 내내 "돌아가긴 하는데 왜 되는지 모르는 코드"를 낳습니다.

## 3. 트랙별 코드 작성 규칙

### 🟦 백엔드 (Java / Spring Boot)

**패키지 구조 — 도메인형으로 (계층형 X)**

```
com.myapp
├─ book
│   ├─ BookController.java
│   ├─ BookService.java
│   ├─ BookRepository.java
│   ├─ Book.java            (Entity)
│   └─ dto/
│       ├─ BookCreateRequest.java   (record)
│       └─ BookResponse.java        (record)
├─ member/ ...
├─ common
│   ├─ exception/
│   └─ response/ApiResponse.java
└─ config/
```

**필수 규칙 10개**

1. **생성자 주입만.** `@Autowired` 필드 주입 ❌ → `private final` + 생성자 (또는 `@RequiredArgsConstructor`)
2. **Entity를 컨트롤러 밖으로 내보내지 않는다.** 반드시 **DTO(record)** 로 변환.
3. **DTO는 `record`로.** `record BookResponse(Long id, String title) {}`
4. **`@Transactional`은 Service에.** Controller·Repository에 붙이지 않습니다. 조회는 `readOnly = true`.
5. **예외는 전역에서.** 각 컨트롤러의 `try/catch` ❌ → `@RestControllerAdvice` 한 곳.
6. **상태코드를 제대로.** 생성 201, 삭제 204, 없음 404, 검증 실패 400, 인증 401, 권한 403.
7. **매직값 금지.** `if (status == 1)` ❌ → `if (status == BookStatus.READ)` (enum)
8. **메서드는 20줄 이내.** 넘으면 무조건 쪼갤 수 있습니다.
9. **Service는 Controller를 모른다.** 의존 방향은 항상 `Controller → Service → Repository` 한 방향.
10. **로그는 `log.info`, `System.out.println` ❌.** (Lombok `@Slf4j`)

**좋은 예 / 나쁜 예**

```java
// ❌ 나쁨 — Entity 노출, 필드 주입, 예외 없음, 상태코드 대충
@RestController
public class BookController {
    @Autowired BookRepository repo;

    @GetMapping("/book")
    public Book get(Long id) {
        return repo.findById(id).get();   // 없으면 터짐
    }
}

// ⭕ 좋음
@RestController
@RequestMapping("/api/books")
@RequiredArgsConstructor
public class BookController {

    private final BookService bookService;

    @GetMapping("/{id}")
    public BookResponse getBook(@PathVariable Long id) {
        return bookService.findById(id);   // 없으면 서비스가 BookNotFoundException → 전역 핸들러가 404
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public BookResponse create(@RequestBody @Valid BookCreateRequest request) {
        return bookService.create(request);
    }
}
```

### 🟨 프론트엔드 (TypeScript / React)

**폴더 구조 — 기능(feature) 단위로**

```
src/
├─ features/
│   └─ book/
│       ├─ components/BookList.tsx
│       ├─ hooks/useBooks.ts
│       ├─ api/bookApi.ts
│       └─ types.ts
├─ shared/
│   ├─ ui/          (Button, Input — shadcn/ui)
│   ├─ lib/         (axios 인스턴스, 유틸)
│   └─ hooks/
└─ app/ 또는 pages/
```

**필수 규칙 10개**

1. **`any` 금지.** 모르겠으면 `unknown` 쓰고 좁혀나갑니다. `strict: true`는 1일차부터.
2. **API 응답 타입을 먼저 정의하고 코드를 짠다.** 백엔드 Swagger를 보고 손으로 옮기세요.
3. **`fetch`는 컴포넌트 안에서 직접 호출 ❌** → `api/` 레이어 → `useQuery` 훅으로 감쌉니다.
4. **서버 데이터 = TanStack Query, UI 상태 = useState/Zustand.** 이 경계를 절대 섞지 않습니다.
5. **컴포넌트는 150줄 이내.** 넘으면 쪼갭니다. 파일 하나에 컴포넌트 하나.
6. **로딩·에러·빈 상태를 항상 함께 만든다.** 성공 화면만 만든 코드는 미완성입니다.
7. **`key`에 배열 index ❌** → 고유 id.
8. **`useEffect`로 데이터 페칭 ❌** (2026년) → TanStack Query 또는 서버 컴포넌트.
9. **`useMemo`/`useCallback` 남용 금지.** React Compiler가 처리합니다. **측정 없이 최적화하지 않습니다.**
10. **`'use client'`는 최대한 아래(잎)에.** 상호작용이 필요한 컴포넌트에만.

```tsx
// ❌ 나쁨
function BookList() {
  const [data, setData] = useState<any>([]);          // any
  useEffect(() => {                                    // 페칭을 effect로
    fetch("/api/books").then(r => r.json()).then(setData);
  }, []);
  return <ul>{data.map((b: any, i: number) => <li key={i}>{b.title}</li>)}</ul>;  // key=index
}

// ⭕ 좋음
type Book = { id: number; title: string; author: string };

const fetchBooks = async (): Promise<Book[]> =>
  (await api.get<Book[]>("/api/books")).data;

function BookList() {
  const { data, isLoading, error } = useQuery({ queryKey: ["books"], queryFn: fetchBooks });

  if (isLoading) return <ListSkeleton />;
  if (error)     return <ErrorMessage message="목록을 불러오지 못했어요" />;
  if (!data?.length) return <EmptyState text="아직 등록된 책이 없어요" />;

  return <ul>{data.map(b => <BookItem key={b.id} book={b} />)}</ul>;
}
```

### 🟩 안드로이드 (Kotlin / Compose)

**모듈 구조**

```
app/src/main/java/com/myapp/
├─ ui/
│   ├─ book/
│   │   ├─ BookListScreen.kt      (@Composable — 상태를 받기만)
│   │   ├─ BookListViewModel.kt
│   │   └─ BookListUiState.kt
│   └─ theme/
├─ data/
│   ├─ remote/  (Retrofit ApiService, DTO)
│   ├─ local/   (Room Entity, Dao)
│   └─ repository/BookRepositoryImpl.kt
├─ domain/  (모델, Repository 인터페이스)
└─ di/      (Hilt 모듈)
```

**필수 규칙 10개**

1. **`!!` 금지.** null 안정성을 무력화하는 순간 Kotlin을 쓰는 이유가 사라집니다.
2. **Composable은 상태를 만들지 않고 받는다** (상태 호이스팅). `value` + `onEvent` 형태.
3. **UI 상태는 `data class` 하나로.** 변수 5개 흩뿌리지 말 것.
4. **Composable 안에서 네트워크 호출 ❌** → ViewModel의 `viewModelScope`.
5. **`collectAsStateWithLifecycle()` 사용.** (`collectAsState()` 아님 — 백그라운드에서 낭비)
6. **`Modifier`는 항상 첫 번째 선택적 파라미터로.** `fun BookItem(book: Book, modifier: Modifier = Modifier)`
7. **`@Preview`를 화면마다 붙인다.** 빌드 안 하고 확인 → 하루 30분 절약.
8. **DTO ↔ 도메인 모델을 분리.** 서버 응답 클래스를 화면까지 끌고 가지 않습니다.
9. **하드코딩 문자열 ❌** → `strings.xml`.
10. **Composable 함수는 `Unit` 반환 + 부수효과 없음.** 값을 반환하지 않습니다.

```kotlin
// ❌ 나쁨 — 화면이 상태를 직접 만들고 네트워크까지 호출
@Composable
fun BookListScreen() {
    var books by remember { mutableStateOf(emptyList<BookDto>()) }
    LaunchedEffect(Unit) { books = RetrofitClient.api.getBooks() }  // 예외 처리도 없음
    LazyColumn { items(books) { Text(it.title!!) } }                // !! 사용
}

// ⭕ 좋음
@Composable
fun BookListRoute(viewModel: BookListViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    BookListScreen(uiState = uiState, onRetry = viewModel::load)
}

@Composable
fun BookListScreen(
    uiState: BookListUiState,
    onRetry: () -> Unit,
    modifier: Modifier = Modifier,
) {
    when {
        uiState.isLoading -> LoadingIndicator(modifier)
        uiState.error != null -> ErrorView(uiState.error, onRetry, modifier)
        uiState.books.isEmpty() -> EmptyView(modifier)
        else -> LazyColumn(modifier) {
            items(uiState.books, key = { it.id }) { BookItem(it) }
        }
    }
}
```

## 4. Git — 첫날부터 실무처럼

### 커밋 메시지 (Conventional Commits)

```
feat: 책 목록 조회 API 추가
fix: 토큰 만료 시 무한 리다이렉트 수정
refactor: BookService 예외 처리 분리
test: BookService 단위 테스트 추가
docs: README에 실행 방법 추가
chore: Gradle 의존성 정리
style: 코드 포맷 정리
```

### 규칙

- **하루 최소 1커밋.** 안 되는 날은 TIL이라도.
- **커밋 단위 = 의미 단위.** "오늘 한 거 전부" ❌
- 브랜치: `main` (배포) / `feat/book-list` (기능) — 혼자여도 브랜치 → PR → merge 연습
- **PR 셀프 리뷰**: merge 전에 diff를 직접 읽고 코멘트를 답니다. 이게 협업 준비의 전부입니다.
- `.gitignore` 필수: `.env`, `application-local.yml`, `*.keystore`, `local.properties`, `node_modules/`, `build/`
- ⛔ **비밀키·DB 비밀번호·JWT 시크릿·API 키를 절대 커밋하지 않습니다.** 한 번 push되면 히스토리에 영구히 남습니다.

## 5. 테스트 — 언제부터, 어떻게

**19주차 전에는 테스트를 안 써도 됩니다.** 문법도 모르는 상태에서 테스트는 사치입니다.
19주차부터는 **"기능 하나 = 테스트 하나"** 를 지킵니다.

| 트랙 | 도구 | 첫 테스트로 뭘 쓸까 |
|------|------|---------------------|
| 🟦 | JUnit5 + AssertJ + Testcontainers | "책을 저장하면 조회된다" |
| 🟨 | Vitest + Testing Library + Playwright | "버튼을 누르면 목록에 항목이 추가된다" |
| 🟩 | JUnit + Turbine + `createComposeRule` | "로딩 상태면 스피너가 보인다" |

테스트 작성 3단계 (Given-When-Then):

```java
@Test
void 책을_저장하면_조회된다() {
    // given
    var request = new BookCreateRequest("클린 코드", "로버트 마틴");
    // when
    var saved = bookService.create(request);
    // then
    assertThat(bookService.findById(saved.id()).title()).isEqualTo("클린 코드");
}
```

> 💡 **테스트 메서드 이름은 한글로 써도 됩니다.** (Java/Kotlin 모두 가능) 초보자에겐 오히려 이게 낫습니다.

## 6. AI 사용 규칙 — 2026년에 가장 중요한 챕터 ⚠️

AI로 코드는 5초면 나옵니다. 그래서 **"만들 줄 아는 사람"의 가치가 "설명하고 고칠 줄 아는 사람"으로 이동**했습니다.
면접에서 물어보는 건 "만들었나요"가 아니라 **"왜 그렇게 만들었나요"** 입니다.

### 단계별 허용 범위

| 시기 | 자동완성 | 허용되는 질문 | 금지 |
|------|----------|---------------|------|
| **1~12주** (문법기) | **끄기** ⛔ | "이 에러 메시지가 무슨 뜻이야?" / "클로저를 비유로 설명해줘" | **코드 생성 요청 전면 금지** |
| **13~24주** (프레임워크기) | 켜도 됨 | "내 코드를 리뷰해줘, 문제점만" / "이 두 방식의 트레이드오프는?" | "~~ 만들어줘" ❌ |
| **25~32주** (프로젝트기) | 적극 사용 | 보일러플레이트 생성, 리팩터링 제안, 테스트 케이스 아이디어 | **설명 못 하는 코드 커밋** ❌ |

### 3가지 철칙

1. **30분 룰이 먼저.** 30분 혼자 붙들어본 뒤에만 AI에게 갑니다. 이 30분이 실력입니다.
2. **답이 아니라 원인을 묻습니다.** ❌ "고쳐줘" → ⭕ **"왜 이 에러가 나는지 원인만 설명하고, 코드는 주지 마"**
3. **설명 테스트.** AI가 준 코드를 커밋하기 전, **한 줄씩 소리 내어 설명**합니다. 한 줄이라도 막히면 커밋하지 않습니다.

### AI를 제대로 쓰는 프롬프트 예시

```
❌ "React 로그인 폼 만들어줘"

⭕ "아래는 내가 짠 로그인 폼이야. React 19 + TS strict 기준으로
   ① 타입 안정성 ② 접근성 ③ 에러 처리
   세 관점에서 문제점만 지적해줘. 수정 코드는 주지 말고 이유만 설명해줘."
```

```
⭕ "내가 만든 이 Spring Boot 프로젝트로 신입 면접을 본다고 가정하고,
   면접관 입장에서 날카로운 질문 10개만 뽑아줘."   ← 31~32주에 최고의 활용법
```

> 🎯 **AI 시대의 신입 차별점은 "AI가 짠 코드를 검증하고 책임질 수 있는가"입니다.**
> 그래서 이 플랜은 초반 12주 동안 일부러 AI를 막습니다. 그 12주가 나머지 20주를 결정합니다.

## 9. 코드 셀프 리뷰 체크리스트 (merge 전 항상)
